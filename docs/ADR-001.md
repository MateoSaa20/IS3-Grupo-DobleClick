# ADR-001: Selección de JWT para autenticación y gestión de sesiones

**Estado:** Aceptado

**Fecha:** 2026-06-09

**Decisores:** Juan Pablo Mencia,Fabio Mateo Saavedra

**Relacionado:** Issue #1, project.md, especificación de autenticación del sistema.

## Contexto

El sistema requiere un mecanismo de autenticación y autorización para garantizar que únicamente usuarios registrados puedan acceder a funcionalidades protegidas.

Debido a que la aplicación se diseñó siguiendo una arquitectura basada en API REST, se buscaba una solución que permitiera escalar horizontalmente el backend sin depender del almacenamiento centralizado de sesiones.

Las restricciones identificadas fueron:

* Reducir la complejidad asociada al manejo de sesiones en el servidor.
* Permitir una integración sencilla con aplicaciones frontend y potenciales clientes móviles.
* Utilizar tecnologías ampliamente adoptadas y con soporte de la comunidad.
* Minimizar el impacto en el rendimiento de la aplicación.


## Decisión

Se decide utilizar **JSON Web Tokens (JWT)** como mecanismo principal para la autenticación y autorización de usuarios.

El flujo de autenticación será el siguiente:

1. El usuario envía sus credenciales al endpoint de autenticación.
2. El servidor valida las credenciales contra la base de datos.
3. Si la autenticación es exitosa, el servidor genera un JWT firmado digitalmente.
4. El cliente almacena el token y lo envía en cada solicitud protegida utilizando el encabezado:

```http
Authorization: Bearer <token>
```

5. El servidor valida la firma y la expiración del token antes de procesar cada solicitud.

### Alcance

Esta decisión cubre:

* Autenticación de usuarios.
* Autorización basada en roles o permisos incluidos en el token.
* Protección de endpoints privados de la API.

Esta decisión no cubre:

* Implementación de Single Sign-On (SSO).
* Integración con proveedores externos de identidad (Google, Microsoft, etc.).
* Autenticación multifactor (MFA).

## Alternativas consideradas

### Opción A: JWT (JSON Web Tokens)

#### Pros

* Mantiene una arquitectura stateless.
* Facilita el escalado horizontal de la aplicación.
* Reduce la necesidad de almacenamiento de sesiones en el servidor.
* Amplio soporte en frameworks y bibliotecas modernas.
* Permite incluir información de autorización dentro del propio token.

#### Contras

* La revocación inmediata de tokens es más compleja.
* Un tiempo de expiración muy largo puede aumentar riesgos de seguridad.
* El tamaño del token puede crecer si se agregan demasiados datos.

### Opción B: Sesiones tradicionales almacenadas en servidor

#### Pros

* Revocación inmediata de sesiones.
* Implementación sencilla en aplicaciones monolíticas.
* Mayor control centralizado sobre las sesiones activas.

#### Contras

* Dificulta el escalado horizontal.
* Requiere almacenamiento compartido entre múltiples instancias.
* Incrementa el consumo de recursos del servidor.

### Opción C: OAuth 2.0 con proveedor externo de identidad

#### Pros

* Alto nivel de seguridad.
* Permite autenticación mediante terceros.
* Facilita la implementación de SSO.

#### Contras

* Mayor complejidad de implementación.
* Requiere infraestructura adicional o dependencia de servicios externos.
* Excede las necesidades actuales del proyecto.

## Consecuencias

### Beneficios esperados

* Mejora de la escalabilidad del sistema.
* Reducción de la carga asociada al manejo de sesiones.
* Integración sencilla con clientes web y móviles.

### Costos o riesgos que se aceptan

* Necesidad de implementar estrategias de expiración y renovación de tokens.
* Mayor complejidad para invalidar tokens antes de su vencimiento.
* Requiere una gestión adecuada de claves secretas y políticas de seguridad.

### Impacto en operación y equipo

* El equipo deberá familiarizarse con el manejo seguro de JWT.
* Será necesario definir tiempos adecuados de expiración de tokens.
* Se deberán implementar mecanismos de validación en todos los endpoints protegidos.

## Plan de implementación

### Pasos mínimos para ejecutarla

1. Incorporar una biblioteca para generación y validación de JWT.
2. Implementar el endpoint de autenticación.
3. Generar tokens firmados utilizando una clave secreta segura.
4. Configurar filtros o middleware para validar tokens en solicitudes protegidas.
5. Definir políticas de expiración y renovación de tokens.
6. Realizar pruebas funcionales y de seguridad del mecanismo implementado.

### Dependencias

* Biblioteca de JWT compatible con el framework backend utilizado.
* Sistema de almacenamiento de usuarios y credenciales.
* Configuración segura para el almacenamiento de claves de firma.

### Métrica de éxito

* El 100% de los endpoints protegidos requieren autenticación válida.
* Los usuarios autenticados pueden acceder correctamente a los recursos autorizados.
* No se detectan vulnerabilidades críticas relacionadas con la autenticación durante las pruebas.

## Triggers de revisión

### Qué condiciones obligan a reabrir esta ADR

* Necesidad de implementar Single Sign-On (SSO).
* Incorporación de autenticación mediante proveedores externos.
* Requerimiento de revocación inmediata de tokens a gran escala.
* Identificación de problemas de seguridad relacionados con JWT.
